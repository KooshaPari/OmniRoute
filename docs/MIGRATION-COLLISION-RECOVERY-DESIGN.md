# Migration identity collision recovery design

Status: design only. This is not a recovery command and does not establish that a live database is safe to migrate. Do not apply the examples to a live database.

## Problem and evidence

The legacy ledger identifies an applied migration by numeric version. If that slot is reused for another name, the runner reports a mismatch but treats the on-disk migration as applied. A version/name mismatch does not prove that its physical effects are present or absent. Some migrations transform data, recreate tables, or rebuild FTS, so re-running all mismatches is unsafe.

The current initialization sequence in `src/lib/db/core.ts` creates tables, runs legacy column healers, creates indexes, and seeds the initial ledger entry before `runMigrations`. `migrationRunner.ts` performs compatibility reconciliation before its mismatch warning. Throwing only at that warning can therefore follow writes and block normal startup. The existing rehome and rename helpers update or delete ledger rows. Their compatibility maps are not a general proof that arbitrary mismatches can be replayed.

A read-only snapshot examined separately contained 53 version/name mismatches. The snapshot showed at least a missing `usage_history.cpa_auth_index`, a pre-203 memory FTS schema with 1,255 null `memory_id` values, and the pre-196 token-limit uniqueness constraint. These are snapshot-specific observations, not a license to assume current live state or replay the set.

## Phased delivery

1. **Audit before enforcement.** Add an offline, read-only command that opens an explicitly specified existing database and migration directory without running `core.ts`, registering a writer, creating tables, setting WAL mode, or invoking migration compatibility helpers. Report the database identity, SQLite version, ledger records, installed file names and SHA-256 hashes, collision identities, supported physical checks, and `unknown` for any check that cannot prove the intended effects. Never print credential values. Include a stable hash over the canonical report, without database content or secrets. Audit does not issue a repair authorization.
2. **Separate, exact repair plans.** Define versioned repair recipes for individually supported source/target migration identities and file checksums. Each recipe specifies dependencies, read-only preconditions, exact allowed statements, expected schema and data postconditions, and unchanged-data invariants. Examples 185, 196 and 203 need independent tests and must not be treated as one transaction merely because their versions collide. Unsupported names, duplicate versions, unknown checksums, unknown physical state, changed prerequisites, missing FTS or adapter limitations produce `blocked`, never automatic replay or an inferred success.
3. **Prepare and verify offline.** Against an independently restorable, WAL-consistent execution-boundary backup, generate a canonical, immutable plan bound to database identity, full relevant ledger state, recipe version, migration checksums, prerequisites, backup digest, and declared data effects. Execute it against a disposable restore with the exact production driver and SQLite features; verify full relevant row contents and foreign keys, integrity, feature-specific positive and negative controls, restart and idempotency. Migration 203 also needs FTS insert/update/delete/search witnesses and a reconciliation of changed IDs. Migration 196 needs populated parent/child rows, duplicate rejection and daily/weekly coexistence. A dry run or a passing backup clone alone does not authorize the live operation.
4. **Explicit execution and durable receipts.** Only after a single authorized writer and request/background-work quiescence are established, take and verify a fresh backup. Acquire the database write lock; under that lock recheck the plan identity, ledger, schema, data preconditions, and backup binding. Abort before mutation on any difference. Apply one tested recipe transactionally and record its exact identity and checksum in a separate append-only recovery ledger in the same transaction; retain the original ledger row unchanged. Check results after commit and keep the service quiescent until functional verification and a coordinated resume. A crash or uncertain commit requires inspection of the receipt and state; never blindly replay. Restoration must account for any writes after backup and cannot overwrite them silently.
5. **Startup integration after recovery exists.** Before any schema writes in initialization, consult a read-only audit and recovery receipts. Unknown or unverified collisions must prevent the affected migrations from being silently skipped and must surface a clear recovery state. Define and test an explicit service-level availability policy: a normal unrestricted start with unresolved broken dependencies is not a safe claim, while stopping the only service without a tested offline recovery path can also cause an outage. Ship enforcement only together with its supported recovery and operator workflow. Do not enable a blanket startup refusal against existing installations as a standalone fix.

## Non-negotiable validation

- Deterministic canonical manifest and plan across reordered ledger/file enumeration; test 53 simultaneous collisions, unknown versions, duplicate file slots, names and changed checksums, absent table/column, and unsupported SQLite features.
- Fresh install, ordinary upgrades, no-op startup, previously supported 163/169 compatibility, no writable database creation during audit, and restart after a partially completed recovery.
- Fault injection at backup publication, lock acquisition, precondition check, transaction rollback, commit acknowledgement, and receipt verification; ensure no partial recipe is reported as complete.
- Revalidation under a lock after a concurrent writer changes schema, data or ledger; reject stale plans and checksum mismatches. A lock serializes SQLite writes only while held and is not by itself proof that app requests or scheduled writers have drained.
- Run on the actual supported native adapter and packaging path, with secure database and backup handling. Check existing backups/restores and migrations independently; do not claim runtime, package, deployment or data-preservation proof from source tests.

## Known limits

Physical schema checks cannot establish that historical data updates occurred. A checksum identifies the bytes examined, not the safety of a migration. Existing ledger rows do not identify the hash of their original migration file. Provenance and a reviewed recipe are necessary; ambiguous cases remain blocked for manual investigation. The plan must distinguish authorization to examine, simulate, and commit a repair; neither audit nor simulation grants permission to mutate a live database.
